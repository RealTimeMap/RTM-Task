# RTM Task UI

Интерфейс сервиса задач [RTM-Task](../RTM-Task) на Vue 3 + TypeScript + Pinia.
Дизайн — макет «RealTimeMap Tasks» из Claude Design.

## Запуск

```bash
npm install
cp .env.example .env      # указать адреса бэкенда и auth-service
npm run dev
```

Нужен запущенный бэкенд RTM-Task. Dev-сервер проксирует на него `/api/v1`
и `/socket.io` (включая websocket), поэтому в браузере остаётся один
origin и CORS не требуется.

Шлюза при разработке нет, поэтому его роль играет сам dev-сервер: он
валидирует Bearer-токен через `token-validate` в auth-service и
подставляет полученные `X-User-*`, предварительно вычистив те, что мог
прислать клиент. Если `VITE_AUTH_ORIGIN` не задан, вместо валидации
используется статическая подмена из `VITE_DEV_USER_*` — так UI
поднимается и без авторизации.

```bash
npm run build     # проверка типов + production-сборка
npm test          # таблица переходов и правила drag & drop
```

Порт dev-сервера фиксирован (5173): при занятом порту он не уезжает
на соседний, а сообщает об ошибке.

## Развёртывание

Интерфейс собирается и деплоится независимо от бэкенда: свой образ, свой
compose. Связывает их traefik — по домену `task.realtimemap.ru` он
отправляет `/api/v1` и `/socket.io` в бэкенд, остальное сюда.

```bash
docker compose up -d --build
```

Внутри образа статику раздаёт nginx. Он же проксирует `/api/v2/auth`
в auth-service: форма входа обращается к нему, и без прокси браузер ушёл
бы на соседний домен — то есть в CORS и в возню с токеном между доменами.

Адрес auth-service задаётся переменной `AUTH_HOST` (по умолчанию
`realtime-map-backend:8001`) и резолвится **во время запроса**, а не при
старте: иначе nginx падал бы, если auth-service поднялся позже.

Нужны внешние сети `web` (для traefik) и `service-network` (чтобы дотянуться
до auth-service).

Адреса API зашиваются в бандл на этапе сборки, но по умолчанию все
относительные — фронт и API на одном домене, так что переопределять
`VITE_*` при сборке образа обычно не нужно.

## Структура

```
src/
  api/          HTTP-клиент и socket.io-клиент
  stores/       Pinia: сессия, задачи, тосты
  components/   компоненты интерфейса
  lib/          перевод доменных значений в визуальные
  types/        контракты, зеркалящие домен бэкенда
```

## Данные

Списки и мутации идут по REST, изменения приходят push-событиями по
Socket.IO — оба канала обслуживаются одними и теми же use case'ами сервера
и отдают одинаковый JSON.

`stores/tasks.ts` подключается к namespace `/tasks`, подписывается на общий
поток и на поток своих задач, и раскладывает входящие события в тот же
список, что отдал REST. Результат мутации кладётся в стор сразу, не дожидаясь
push, — интерфейс не «прыгает» в ожидании эха.

Фильтры по типу, статусу и поиску применяются на клиенте поверх загруженного
набора: отклик мгновенный. Область видимости («Мои» / «Все») — серверный
фильтр, её смена перезагружает список.

## Вёрстка

Приложение занимает всё окно: сайдбар и шапка фиксированы, прокручивается
только область контента. В макете интерфейс был нарисован «карточкой» на
подложке — со скруглением, тенью и пределом 1440px; для мокапа это нужно,
живому сайту мешает, поэтому обрамление убрано.

Брейкпоинты:

| Ширина | Что меняется |
|---|---|
| ≤ 1200px | таблица списка уходит в горизонтальную прокрутку |
| ≤ 1100px | доска складывается в две колонки |
| ≤ 1000px | сайдбар сужается до 200px, уменьшаются отступы |
| ≤ 900px | окна задачи и создания складываются в одну колонку |
| ≤ 820px | доска складывается в одну колонку |
| ≤ 720px | мобильная раскладка |
| ≤ 480px | компактный экран входа |

Пороги подобраны под реальные ширины с учётом сайдбара: на портретном
iPad (768px) две колонки доски не помещаются, а на ландшафтном (1024px)
таблице списка без прокрутки не хватает места.

### Мобильные устройства

- **Сайдбар** превращается в выдвижное меню поверх контента, открывается
  кнопкой в шапке и закрывается тапом по затемнению или выбором пункта.
- **Шапка** становится двухъярусной: заголовок и кнопка меню сверху,
  поиск и фильтры — вторым рядом во всю ширину.
- **Список задач** перестраивается из таблицы в карточки: приоритет и дата
  прячутся, они видны в окне задачи.
- **Окна задачи и создания** раскрываются на весь экран.

Отдельно от ширины экрана учитывается тип указателя (`pointer: coarse`):

- **Перетаскивание отключается** — HTML5 drag & drop на тач-экранах не
  работает, а атрибут `draggable` мешает прокрутке и вызывает системное
  меню по долгому нажатию. Задачи двигаются стрелками на карточке, они
  увеличены до размера, пригодного для пальца.
- Поля ввода получают шрифт 16px: при меньшем Safari на iOS увеличивает
  страницу при фокусе и обратно не возвращает.
- Подсветка при наведении включается только там, где есть настоящий
  курсор — на тач-экранах она залипает после тапа.
- Цели нажатия увеличиваются до 40–44px: кнопки меню, выхода, фильтров,
  стрелок на карточке и элементов окна задачи.

Раскрытые на весь экран окна и выдвижное меню учитывают `safe-area-inset`:
на iPhone с вырезом содержимое иначе уходит под него и под домашнюю полосу
(в `index.html` для этого стоит `viewport-fit=cover`).

## Окно задачи

Задача открывается модальным окном в две колонки (`TaskDialog.vue`): слева
заголовок и описание, справа статус, метаданные, приоритет, исполнитель и
удаление. Каждая колонка прокручивается сама — длинное описание не уносит
вниз кнопки управления.

Раньше это была боковая панель на 400px: описанию с разметкой там было
тесно, а половина экрана всё равно оставалась пустой.

Закрывается кликом по затемнению, крестиком или Escape. В режиме правки
описания Escape сначала выходит из редактора — иначе одно нажатие теряло бы
черновик. Ниже 900px колонки складываются в одну, на телефоне окно
разворачивается на весь экран.

## Описания задач

Описание пишется в markdown. В базе хранится **сырой текст** — он остаётся
редактируемым и не зависит от того, как мы его показываем; разметка
превращается в HTML только на клиенте (`lib/markdown.ts`).

Поддерживается ограниченный набор: выделение (`**жирный**`, `_курсив_`,
`~~зачёркнутый~~`), `код` и блоки кода, списки, чек-боксы, цитаты, ссылки,
горизонтальная черта. Картинок, таблиц и произвольного HTML нет намеренно —
описанию задачи они не нужны, а поверхность для ошибок увеличивают.

**Безопасность.** Описание пишет пользователь, поэтому результат разбора
обязательно проходит через DOMPurify с белым списком тегов. Скрипты,
обработчики событий, `javascript:`/`data:`-ссылки и iframe вырезаются;
ссылки открываются с `rel="noopener noreferrer nofollow"`. Это покрыто
тестами (`tests/markdown.test.ts`) — их стоит запускать при любых правках
рендеринга.

Редактор (`ui/MarkdownEditor.vue`) даёт панель кнопок и переключатель
«Писать / Предпросмотр», так что знать синтаксис необязательно. Описание
можно править прямо в окне задачи.

## Доска

Карточку можно перетащить в другую колонку — это меняет статус задачи.
Перетаскивание доступно только тем, кто вправе её менять (автор,
исполнитель или менеджер), у остальных карточка не берётся.

Колонка под курсором подсвечивается: синим — переход разрешён, красным —
нет. Допустимость проверяется по той же таблице жизненного цикла, что и на
сервере (`types/task.ts`). Решение всё равно за сервером: клиентская
таблица лишь избавляет от заведомо лишних отказов.

**Задача без исполнителя достаётся тому, кто её взял.** Сервер не пускает
задачу в работу без ответственного, поэтому при переносе ничьей задачи в
«В работе» стор сначала назначает исполнителем текущего пользователя и
только потом меняет статус (`changeStatusAsOwner`). Тост об этом сообщает.
Так же ведут себя стрелки на карточке.

Кнопки-стрелки на карточке остаются как альтернатива перетаскиванию —
они работают с клавиатуры и на тач-устройствах.

Тело карточки намеренно сделано `<div role="button">`, а не `<button>`:
нативная кнопка перехватывает `mousedown` и не даёт начать перетаскивание,
из-за чего карточку удавалось взять только за узкую полоску футера.

## Вход

Форма входа отправляет логин и пароль в **auth-service платформы** —
RTM-Task паролей не хранит и не проверяет. В ответ приходит
Bearer-токен (`access_token`), он кладётся в `localStorage` и
прикладывается ко всем запросам.

Дальше работает шлюз: он через forward auth валидирует токен в
`GET /auth/token-validate` и подставляет заголовки
`X-User-ID` / `X-User-Name` / `X-User-Admin`. Фронтенд их не формирует —
подделать личность с клиента нельзя.

После входа приложение спрашивает `GET /staff/me`: кем нас считают.
401 — токен отсутствует или протух (тогда он стирается и показывается
форма); 403 — вход прошёл, но доступ в таск-менеджер есть только
у администраторов платформы.

Сотрудник заводится сервисом сам при первом обращении, поэтому
регистрации в таск-менеджере нет — она живёт в auth-service.

**Имена с кириллицей.** HTTP-заголовки не переносят не-ASCII, поэтому
`X-User-Name` приходит percent-encoded; бэкенд его декодирует.

## Права

`types/staff.ts` повторяет матрицу ролей бэкенда, чтобы прятать недоступные
действия. Это только подсказка интерфейса — решение всегда за сервером,
и его отказ (403) показывается пользователю баннером.

Так же устроены переходы статусов: `types/task.ts` дублирует таблицу
жизненного цикла, чтобы заранее гасить кнопки, но допустимость перехода
проверяет сервер.

## Отличия от макета

Макет рисовался до появления бэкенда, поэтому часть сущностей в нём не
имеет опоры в API и в интерфейс не вошла: чек-листы, комментарии, спринты,
оценка в часах и типы «дизайн» / «техдолг». Типы задач — `bug` / `feature` /
`fix`, как в домене.

Добавлено то, чего в макете не было: индикатор состояния realtime-соединения
в шапке, выбор исполнителя и удаление задачи в окне задачи.

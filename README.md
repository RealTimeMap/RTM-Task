# RTM Task UI

Интерфейс сервиса задач [RTM-Task](../RTM-Task) на Vue 3 + TypeScript + Pinia.
Дизайн — макет «RealTimeMap Tasks» из Claude Design.

## Запуск

```bash
npm install
cp .env.example .env      # указать адреса бэкенда и auth-service
npm run dev
```

Нужен запущенный бэкенд RTM-Task. Dev-сервер проксирует на него `/api/v1`
и `/socket.io` (включая websocket), поэтому в браузере остаётся один
origin и CORS не требуется.

Шлюза при разработке нет, поэтому его роль играет сам dev-сервер: он
валидирует Bearer-токен через `token-validate` в auth-service и
подставляет полученные `X-User-*`, предварительно вычистив те, что мог
прислать клиент. Если `VITE_AUTH_ORIGIN` не задан, вместо валидации
используется статическая подмена из `VITE_DEV_USER_*` — так UI
поднимается и без авторизации.

```bash
npm run build     # проверка типов + production-сборка
npm test          # переходы, drag & drop, ошибки auth, markdown, доработка,
                  # обсуждение, сортировка
```

Порт dev-сервера фиксирован (5173): при занятом порту он не уезжает
на соседний, а сообщает об ошибке.

## Развёртывание

Интерфейс живёт в отдельном репозитории и деплоится независимо от
бэкенда: свой образ, свой compose. Связывает их traefik — по домену
`task.realtimemap.ru` он отправляет `/api/v1` и `/socket.io` в бэкенд,
остальное сюда.

| Часть | Репозиторий | Образ |
|---|---|---|
| Интерфейс | `RealTimeMap/RTM-Task` | `ghcr.io/realtimemap/rtm-task` |
| Бэкенд | `RealTimeMap/RTM-Task-backend` | `ghcr.io/realtimemap/rtm-task-backend` |

Образ собирает и публикует GitHub Actions (`.github/workflows/build.yml`)
при push в основную ветку и по тегам `v*`.

```bash
cp .env.production.example .env
docker compose up -d
```

`.env` рядом с `docker-compose.yml` читает сам compose:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `TAG` | версия образа | `latest` |
| `APP_DOMAIN` | домен в traefik-labels | `task.realtimemap.ru` |
| `AUTH_HOST` | куда nginx проксирует `/api/v2/auth` | `realtime-map-backend:8001` |

Все три имеют дефолты, так что без `.env` compose тоже поднимется —
файл нужен, чтобы менять версию образа и домен, не трогая репозиторий.

Внутри образа статику раздаёт nginx. Он же проксирует `/api/v2/auth`
в auth-service: форма входа обращается к нему, и без прокси браузер ушёл
бы на соседний домен — то есть в CORS и в возню с токеном между доменами.

Адрес auth-service задаётся переменной `AUTH_HOST` (по умолчанию
`realtime-map-backend:8001`) и резолвится **во время запроса**, а не при
старте: иначе nginx падал бы, если auth-service поднялся позже.

Нужны внешние сети `web` (для traefik) и `service-network` (чтобы дотянуться
до auth-service).

**Переменных `VITE_*` в проде нет.** Они читаются либо dev-сервером
(`vite.config.ts`), либо попадают в бандл со значениями по умолчанию —
а дефолты как раз продовые: всё живёт на одном домене, поэтому адреса
относительные.

| Переменная | Где работает | Значение в проде |
|---|---|---|
| `VITE_API_URL` | бандл | `/api/v1` (дефолт) |
| `VITE_SOCKET_URL` | бандл | пусто = тот же хост |
| `VITE_AUTH_BASE_PATH` | бандл | `/api/v2/auth` (дефолт) |
| `VITE_BACKEND_ORIGIN` | только dev-сервер | не используется |
| `VITE_AUTH_ORIGIN` | только dev-сервер | не используется |
| `VITE_TUNNEL_HOST` | только dev-сервер | не используется |
| `VITE_DEV_USER_*` | только dev-сервер | не используется |

Единственная переменная, которая настраивается в проде, — `AUTH_HOST`
для nginx (задана в `docker-compose.yml`).

Файл `.env` в образ не попадает: он в `.dockerignore`.

## Структура

```
src/
  api/          HTTP-клиент и socket.io-клиент
  stores/       Pinia: сессия, задачи, обсуждение открытой задачи, тосты
  components/   компоненты интерфейса
  lib/          перевод доменных значений в визуальные
  types/        контракты, зеркалящие домен бэкенда
```

## Данные

Списки и мутации идут по REST, изменения приходят push-событиями по
Socket.IO — оба канала обслуживаются одними и теми же use case'ами сервера
и отдают одинаковый JSON.

`stores/tasks.ts` подключается к namespace `/tasks`, подписывается на общий
поток и на поток своих задач, и раскладывает входящие события в тот же
список, что отдал REST. Результат мутации кладётся в стор сразу, не дожидаясь
push, — интерфейс не «прыгает» в ожидании эха.

Фильтры по типу, статусу и поиску применяются на клиенте поверх загруженного
набора: отклик мгновенный. Область видимости («Мои» / «Все») — серверный
фильтр, её смена перезагружает список.

**Сортировка серверная.** В списке задач кликом по заголовку колонки —
тип, статус, приоритет, дата создания; повторный клик разворачивает
направление, стрелка стоит у активной колонки. На узком экране шапка
скрыта, а строки становятся карточками, поэтому там выбор выпадающим
списком с отдельной кнопкой направления. Выбранный порядок сохраняется
в `localStorage` и переживает перезагрузку; значение оттуда проверяется,
а не берётся на веру.

Сортировать на клиенте нельзя: при пагинации это упорядочило бы только
загруженную страницу. Но клиент повторяет сравнение (`sortRank`,
`compareTasks`) — иначе push-события ломали бы расстановку: новая задача
вставала бы в начало любого списка, а сменившая приоритет оставалась бы
на прежнем месте. Ранги статуса и типа берутся из `STATUS_ORDER` и
`TYPE_ORDER`, чтобы совпадать с `CASE`-выражениями сервера.

`stores/discussion.ts` держит обсуждение и чек-лист **только открытой
задачи**: держать их для всей доски значило бы тянуть содержимое каждой
карточки ради одной. Списки загружаются при открытии окна задачи и
обновляются push-событиями, чужие события отбрасываются по `taskId`.

Карточкам на доске хватает сводки — `checklistTotal`, `checklistDone`,
`commentCount`, — которая приходит с загрузкой списка. События изменения
самой задачи сводку не несут, поэтому `upsert` не затирает уже известные
значения отсутствующими: иначе каждое перетаскивание карточки гасило бы
прогресс чек-листа до следующей полной загрузки. Обратный путь —
`applySummary`: изменение обсуждения не меняет саму задачу и её версию,
и счётчик на карточке обновляет стор обсуждения.

**Осторожно с обратной связью.** Эти два пути образуют петлю, и она уже
один раз замыкалась (100+ запросов в секунду на `/tasks/:id/checklist`
в проде): загрузка чек-листа → `syncSummary` → `applySummary` пишет
новый объект задачи → `selected` как computed по списку отдаёт новую
ссылку → окно задачи считает это сменой задачи → снова загрузка.
Разомкнута в трёх местах, каждое из которых достаточно само по себе:

- `TaskDialog` следит за `selected.value?.id`, а не за объектом задачи;
- `applySummary` не трогает список, если значения не изменились;
- `discussion.open` для уже открытой задачи ничего не грузит — списки
  поддерживают realtime-события.

Регрессию стережёт `tests/discussion-loop.test.ts`: он моделирует все
три звена и падает, если сломать любое.

## Вёрстка

Приложение занимает всё окно: сайдбар и шапка фиксированы, прокручивается
только область контента. В макете интерфейс был нарисован «карточкой» на
подложке — со скруглением, тенью и пределом 1440px; для мокапа это нужно,
живому сайту мешает, поэтому обрамление убрано.

Брейкпоинты:

| Ширина | Что меняется |
|---|---|
| ≤ 1200px | таблица списка становится карточками в две колонки |
| ≤ 1100px | доска складывается в две колонки |
| ≤ 1000px | сайдбар сужается до 200px, уменьшаются отступы |
| ≤ 900px | окна задачи и создания складываются в одну колонку |
| ≤ 820px | доска складывается в одну колонку |
| ≤ 720px | мобильная раскладка |
| ≤ 480px | компактный экран входа |

Пороги подобраны под реальные ширины с учётом сайдбара: на портретном
iPad (768px) две колонки доски не помещаются, а таблице списка семь колонок
требуют ~900px — столько остаётся только от 1200px ширины окна. Ниже этого
порога список показывается карточками, а не горизонтальной прокруткой:
таблицу, которую надо листать вбок, читать неудобно.

### Мобильные устройства

- **Сайдбар** превращается в выдвижное меню поверх контента, открывается
  кнопкой в шапке и закрывается тапом по затемнению или выбором пункта.
- **Шапка** становится двухъярусной: заголовок и кнопка меню сверху,
  поиск и фильтры — вторым рядом во всю ширину.
- **Список задач** — те же карточки, но в один столбец и без приоритета
  с датой: они видны в окне задачи, а ширина здесь дороже.
- **Окна задачи и создания** раскрываются на весь экран.

Отдельно от ширины экрана учитывается тип указателя (`pointer: coarse`):

- **Перетаскивание отключается** — HTML5 drag & drop на тач-экранах не
  работает, а атрибут `draggable` мешает прокрутке и вызывает системное
  меню по долгому нажатию. Задачи двигаются стрелками на карточке, они
  увеличены до размера, пригодного для пальца.
- Поля ввода получают шрифт 16px: при меньшем Safari на iOS увеличивает
  страницу при фокусе и обратно не возвращает.
- Подсветка при наведении включается только там, где есть настоящий
  курсор — на тач-экранах она залипает после тапа.
- Цели нажатия увеличиваются до 40–44px: кнопки меню, выхода, фильтров,
  стрелок на карточке и элементов окна задачи.

Раскрытые на весь экран окна и выдвижное меню учитывают `safe-area-inset`:
на iPhone с вырезом содержимое иначе уходит под него и под домашнюю полосу
(в `index.html` для этого стоит `viewport-fit=cover`).

## Окно задачи

Задача открывается модальным окном в две колонки (`TaskDialog.vue`): слева
заголовок и описание, справа статус, метаданные, приоритет, исполнитель и
удаление. Каждая колонка прокручивается сама — длинное описание не уносит
вниз кнопки управления.

Раньше это была боковая панель на 400px: описанию с разметкой там было
тесно, а половина экрана всё равно оставалась пустой.

Закрывается кликом по затемнению, крестиком или Escape. Escape снимает
верхний открытый слой: сначала список исполнителей, затем режим правки
описания, и только потом само окно — иначе одно случайное нажатие теряло
бы черновик.

Список исполнителей раскрывается поверх содержимого (`position: absolute`),
а не в потоке: иначе он раздвигал бы блоки под собой и окно подпрыгивало
при каждом открытии. Направление — вверх: поле стоит внизу колонки, и вниз
список упёрся бы в её край. Ниже 900px колонки складываются в одну, на телефоне окно
разворачивается на весь экран.

## Описания задач

Описание пишется в markdown. В базе хранится **сырой текст** — он остаётся
редактируемым и не зависит от того, как мы его показываем; разметка
превращается в HTML только на клиенте (`lib/markdown.ts`).

Поддерживается ограниченный набор: выделение (`**жирный**`, `_курсив_`,
`~~зачёркнутый~~`), `код` и блоки кода, списки, чек-боксы, цитаты, ссылки,
горизонтальная черта. Картинок, таблиц и произвольного HTML нет намеренно —
описанию задачи они не нужны, а поверхность для ошибок увеличивают.

**Безопасность.** Описание пишет пользователь, поэтому результат разбора
обязательно проходит через DOMPurify с белым списком тегов. Скрипты,
обработчики событий, `javascript:`/`data:`-ссылки и iframe вырезаются;
ссылки открываются с `rel="noopener noreferrer nofollow"`. Это покрыто
тестами (`tests/markdown.test.ts`) — их стоит запускать при любых правках
рендеринга.

Редактор (`ui/MarkdownEditor.vue`) даёт панель кнопок и переключатель
«Писать / Предпросмотр», так что знать синтаксис необязательно. Описание
можно править прямо в окне задачи.

## Доска

Карточку можно перетащить в другую колонку — это меняет статус задачи.
Перетаскивание доступно только тем, кто вправе её менять (автор,
исполнитель или менеджер), у остальных карточка не берётся.

Колонка под курсором подсвечивается: синим — переход разрешён, красным —
нет. Допустимость проверяется по той же таблице жизненного цикла, что и на
сервере (`types/task.ts`). Решение всё равно за сервером: клиентская
таблица лишь избавляет от заведомо лишних отказов.

**Задача без исполнителя достаётся тому, кто её взял.** Сервер не пускает
задачу в работу без ответственного, поэтому при переносе ничьей задачи в
«В работе» стор сначала назначает исполнителем текущего пользователя и
только потом меняет статус (`changeStatusAsOwner`). Тост об этом сообщает.
Так же ведут себя стрелки на карточке.

Кнопки-стрелки на карточке остаются как альтернатива перетаскиванию —
они работают с клавиатуры и на тач-устройствах.

Тело карточки намеренно сделано `<div role="button">`, а не `<button>`:
нативная кнопка перехватывает `mousedown` и не даёт начать перетаскивание,
из-за чего карточку удавалось взять только за узкую полоску футера.

## Вход

Форма входа отправляет логин и пароль в **auth-service платформы** —
RTM-Task паролей не хранит и не проверяет. В ответ приходит
Bearer-токен (`access_token`), он кладётся в `localStorage` и
прикладывается ко всем запросам.

Дальше работает шлюз: он через forward auth валидирует токен в
`GET /auth/token-validate` и подставляет заголовки
`X-User-ID` / `X-User-Name` / `X-User-Admin`. Фронтенд их не формирует —
подделать личность с клиента нельзя.

После входа приложение спрашивает `GET /staff/me`: кем нас считают.
401 — токен отсутствует или протух (тогда он стирается и показывается
форма); 403 — вход прошёл, но доступ в таск-менеджер есть только
у администраторов платформы.

Сотрудник заводится сервисом сам при первом обращении, поэтому
регистрации в таск-менеджере нет — она живёт в auth-service.

**Имена с кириллицей.** HTTP-заголовки не переносят не-ASCII, поэтому
`X-User-Name` приходит percent-encoded; бэкенд его декодирует.

## Права

`types/staff.ts` повторяет матрицу ролей бэкенда, чтобы прятать недоступные
действия. Это только подсказка интерфейса — решение всегда за сервером,
и его отказ (403) показывается пользователю баннером.

Так же устроены переходы статусов: `types/task.ts` дублирует таблицу
жизненного цикла, чтобы заранее гасить кнопки, но допустимость перехода
проверяет сервер.

## Доработка

Завершённую задачу нельзя перетащить обратно на доске: из `complete`
переходов в таблице нет. Вернуть её можно только кнопкой «Отправить
в доработку» в окне задачи — она открывает поле с обязательным описанием
того, что нужно доделать (markdown, как и описание задачи).

Задача уходит в «В работе» к своему исполнителю, а если исполнителя нет —
в «Новые». Замечание показывается баннером над описанием, пока задачу не
примут заново: это текущее задание, а не история. Исполнителю уходит письмо,
если у него заполнен email и в доработку отправил не он сам.

## Обсуждение и чек-лист

В окне задачи под описанием живёт обсуждение, справа рядом с управлением —
чек-лист: это план работ, а не текст задачи, и отмечают пункты по ходу дела.

Комментарии пишутся в markdown тем же редактором, что и описание. Свой
текст можно править и удалять, чужой — только `admin`/`manager`; правленый
помечается «изменено». Комментировать можно и завершённую задачу: вопросы
к результату возникают именно после сдачи.

Чек-лист заполняется **прямо в форме создания** — план работ обычно известен
в момент заведения задачи. Незакоммиченный ввод из поля тоже уходит вместе
с формой: пользователь набрал пункт и нажал «Создать», не нажав «Добавить».
Отметка пункта ставится оптимистично — щелчок по чек-боксу отзывается сразу,
при отказе сервера состояние возвращается. У закрытой задачи чек-лист
только для чтения, но прогресс завершению не мешает: незакрытый пункт
не блокирует переход в «Завершена».

На карточке появляются значки: прогресс чек-листа и число комментариев —
только когда есть что показать, иначе доска превратилась бы в таблицу
счётчиков. Закрытый чек-лист подсвечивается зелёным.

**Раскладка окна.** На широком экране это две колонки и две строки:
слева описание, под ним обсуждение со своей прокруткой, справа во всю
высоту — управление задачей. Описание занимает столько, сколько ему
нужно, а остаток высоты забирает переписка — так она листается, не
утягивая за собой заголовок.

Ниже 900px колонки складываются в одну, и порядок блоков меняется через
`order`: чек-лист поднимается к статусу, а обсуждение уходит в самый
низ. В два столбца переписка стоит сбоку и никому не мешает, но в одном
она растёт неограниченно — и до плана работ пришлось бы прокручивать всё
обсуждение, хотя открывают задачу обычно ради него. Ради этой
перестановки обсуждение вынесено из левой колонки в прямые дети сетки:
переставить по `order` можно только их.

## Отличия от макета

Макет рисовался до появления бэкенда, поэтому часть сущностей в нём не
имеет опоры в API и в интерфейс не вошла: спринты, оценка в часах
и типы «дизайн» / «техдолг». Типы задач — `bug` / `feature` /
`fix` / `refactor` / `update`, как в домене; порядок и подписи заданы
в `lib/presentation.ts` (`TYPE_ORDER`), фильтры и форма создания берут
список оттуда.

Добавлено то, чего в макете не было: индикатор состояния realtime-соединения
в шапке, выбор исполнителя и удаление задачи в окне задачи, возврат
завершённой задачи в доработку, смена типа задачи и сортировка списка.
